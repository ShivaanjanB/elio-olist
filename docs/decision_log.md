# Decision log: data model, staging, marts, analytics and recommendation (Phases 3 to 9)

Every design decision made while modelling, with the options considered, the reason, and the evidence. The evidence is reproducible: [`relationship_checks.sql`](relationship_checks.sql) and [`type_and_design_checks.sql`](type_and_design_checks.sql) run read-only against the loaded `RAW` tables. The design itself is in [`data_model.md`](data_model.md). Ingest decisions are in [`../ingest/LOAD_NOTES.md`](../ingest/LOAD_NOTES.md).

Date of entries D01 to D62: 2026-11-13; D63 to D70: 2026-11-14. Status of all entries: accepted.

## How the decisions were made

dbt Labs' analytics-engineering practice and the usual staging / intermediate / marts conventions set the method:

1. **Look at the data before modelling it.** No decision below rests on an assumption that a query could settle.
2. **Plan backwards from the output.** The five analytics questions (top categories, monthly trend, anomalies, breakdown by state, repeat rate by first-order experience) fix which columns the marts need, which fixes the intermediate models, which fixes the staging models.
3. **Reuse before adding a model.** A new model needs a reason: a different grain, or logic two models share.
4. **Let dbt build the layers.** `STAGING`, `INTERMEDIATE` and `MARTS` are created by dbt, never by hand-run SQL.

No third-party reference was followed for the normalisation itself, so its reasoning is written out in `data_model.md`.

## Decisions

| ID | Decision | Alternatives considered | Why | Evidence |
|---|---|---|---|---|
| D01 | Design backwards from the five analytics questions | Design from the source tables forwards | A mart column with no question behind it is clutter, and a question with no column is a gap. Working backwards fixes both. | The traced requirements table in `data_model.md` |
| D02 | Four schemas in `ELIO_OLIST`: `RAW` (loaded by the ingest scripts), `STAGING`, `INTERMEDIATE` and `MARTS` (built by dbt). Override `generate_schema_name` so the schemas are named exactly that. | Let dbt prefix schema names with the target schema (`RAW_STAGING`) | Exact names make the layers readable and the queries predictable. dbt's default naming is built for shared dev environments, which this project does not have. | brief A2 |
| D03 | Materialisation: staging = **views**, intermediate = **views**, marts = **tables** | Intermediate as `ephemeral` (a common default); everything as tables | Views for staging: always current, no storage, and 1:1 with the source. Intermediate as views rather than ephemeral so each roll-up can be queried and tested on its own while debugging; the data is small enough that the cost is nothing. Marts as tables: they are what analysts hit, so the join work is paid once. | 112,650 rows in the largest source |
| D04 | Staging is **1:1 with the source files** (eight `stg_olist__*` models). Cleaning is limited to renaming, casting types and removing duplicates that break a key. | Put business logic (joins, rules) in staging | Keeps staging boring and auditable: anything surprising is in intermediate or marts, where it is named. | dbt convention: staging is 1:1 with the source |
| D05 | The 3NF entities `customer` and `customer_address` map to **different models**: `customer_address` is the `customers` source file (keyed by `customer_id`), and `customer` (keyed by `customer_unique_id`) is derived in intermediate | Split the source into two staging models | A staging model per source file is the dbt convention (D04). The person only exists as a derived thing, so deriving it where the logic lives is honest. | 99,441 `customer_id`s but 96,096 people |
| D06 | Naming: `stg_olist__<entity>`, `int_<what>`, `dim_<entity>`, `fct_<event>`; snake_case; fix the misspelt `product_name_lenght` and `product_description_lenght` to `_length` in staging only | Keep the source spellings | Renaming once, in staging, means nothing downstream carries a typo, and RAW stays exactly as received. | headers of `olist_products_dataset.csv` |
| D07 | **Column types** (full table in `data_model.md`): ids `VARCHAR(32)`, state `VARCHAR(2)`, zip prefix `VARCHAR(5)`, timestamps `TIMESTAMP_NTZ`, money `NUMBER(12,2)`, whole numbers `NUMBER(10,0)`, review score `NUMBER(1,0)`, free text plain `VARCHAR` | Looser (all `NUMBER`, all `VARCHAR`) or tighter per-column sizes | A type is a promise about the data, so each was checked: all 12 id columns are exactly 32 characters with no blanks; all 8 timestamp columns parse with 0 failures; money has no value with more than 2 decimals (price max 6,735.00; payment max 13,664.08); every whole-number column has 0 decimal points; scores are 1 to 5; states are 2 characters. Free text gets no length because declaring one adds nothing in Snowflake. Fixed-width codes get exact widths because their width is part of their meaning. | `type_and_design_checks.sql` sections 1 to 6 |
| D08 | **Zip prefixes stay text**, `VARCHAR(5)` | Numeric zip | Numbers drop the leading zero: 23,995 customer and 1,027 seller prefixes start with `0`. | `ingest/05_check_loaded_data.sql` |
| D09 | **No time-zone conversion.** `TIMESTAMP_NTZ`; the source's local time is kept as is. | Convert to UTC, or to `America/Sao_Paulo` | The source carries no zone, so any conversion would invent information. Every comparison (late, days to deliver) is between two timestamps from the same source, so a shared offset cancels out. The Brazil-local-time assumption is recorded, not applied. | source format `YYYY-MM-DD HH24:MI:SS` |
| D10 | Keys: **natural keys in staging and intermediate; surrogate keys on the dimensions in marts** (`customer_sk`, `product_sk`, `seller_sk`, via a local `generate_surrogate_key` macro, see D30 and D42). Facts carry the dimensions' surrogate keys. `fct_orders` keeps `order_id` as its key; `fct_order_items` has a one-column key, `order_item_key`, because its natural key is two columns. | Natural keys everywhere; surrogate keys on every fact | Here a surrogate key is a **convention, not a protection**. It is a deterministic hash of the natural key, so it does NOT insulate the marts from a change to a source key (the hash would change too), and it is not what would make history tracking possible (D28 rules that out). What it gives is one uniform single-column join key on every dimension, the same key after every rebuild, and a single-column primary key on the item fact. The price is one extra 32-character column per table. *Corrected in Phase 5: the first wording claimed insulation from source-key changes, which is not true of a hash.* | star-schema convention (brief A2) |
| D11 | **Constraints are tested, not declared.** `unique`, `not_null`, `relationships` and `unique_combination_of_columns` tests on every key at every layer, plus enforced model contracts on the marts. | Declare primary and foreign keys | Snowflake does not enforce them, so a declared key would be a comment pretending to be a guarantee. A failing test is a real signal. | Snowflake documentation |
| D12 | **The person dimension is at `customer_unique_id` grain** (`dim_customer`). Its location is taken from the person's **first order**; every address stays in the 3NF `customer_address`. | `customer_id` grain (a person per order); latest order's location | `customer_id` is new on every order, so repeat purchase would measure about 0%. First-order location is stable and matches the first-order analysis. Locations do differ for some people, so a rule is needed. | 2,997 people have several ids; 39 span different states, 250 different zips |
| D13 | **First order = the person's earliest purchase timestamp, ties broken by `order_id`** (ascending) | Leave ties arbitrary | A tie broken arbitrarily would make the first order, and so the repeat-rate cohort, change between runs. | 276 people have their first order tied on the timestamp |
| D14 | **One review per order: the latest** (by `review_answer_timestamp`, then `review_id`), plus a `review_count` so multiple reviews stay visible. Orders with no review get a NULL score, never 0. | Average the scores; keep the best or worst; keep all (fan-out) | One satisfaction signal per order is what the order-grain fact needs. An average would invent non-integer scores and blend an old opinion with a new one, and the latest review is the customer's final word. A NULL stays honest about 768 orders having no review. | 547 orders have several reviews; 0 ties on the answer time |
| D15 | **Payments roll up to order grain** (`int_order_payments`): `payment_total`, `payment_count`, `installments_max`, `primary_payment_type` (the type with the largest value) | Join payments to items directly | Joining at item grain repeats each item once per payment and inflates every total. | Demonstrated: `SUM(payment_value)` +26.9%, `SUM(price)` +4.5% |
| D16 | **Revenue = item `price`, excluding freight.** `gmv = price + freight_value`. `payment_total` is kept separately as cash collected. | Revenue = payment value; revenue = price + freight | Only items can be attributed to a category, product or seller, which the analytics need, and payments exist only at order grain. Items reconcile to payments: `price + freight` totals 15.84M against 16.01M of payments (a 1.0% gap), and per order they agree within 1.00 for 98,416 of 98,665 orders (99.75%). The gap is financing, vouchers and orders without items. | `type_and_design_checks.sql` section 11 |
| D17 | **Canceled and unavailable orders do not count as revenue** (`is_revenue_order = false`). In-flight statuses (shipped, invoiced, processing, approved, created) do count. | Count everything; count only delivered | Money for a canceled order was never collected, and an in-flight order is a real committed sale. The effect is small and visible: 467 such orders hold 97,242.96 of item value, 0.72% of the total. | section 17: canceled 95,235.27 and unavailable 2,007.69 |
| D18 | **"Late" is measured at date grain:** delivered date is later than the estimated date | Compare as full timestamps | Every estimated delivery date sits at exactly 00:00:00. A timestamp comparison would flag anything delivered on the estimated day after midnight, which is not late. | 7,826 orders late as timestamps against **6,534 (6.77%)** as dates: 1,292 same-day deliveries would be wrongly flagged |
| D19 | **Delivery metrics use only orders with status `delivered` and a customer-delivery date** | Use every order with a date; fill missing dates | A metric on an order that never arrived is meaningless. The exclusions are small and named. | 96,470 orders qualify; 8 delivered orders have no date; 6 non-delivered orders have one |
| D20 | **Out-of-order timestamps are kept and flagged, not dropped.** `days_to_deliver` runs from purchase to delivery, which is never negative. | Drop rows whose timestamps are out of order | Dropping would silently change the order counts. The metric used does not depend on the odd field. | 23 orders delivered before the carrier pickup date; 0 delivered before purchase |
| D21 | **Orders with no items, payments or reviews are kept in `fct_orders`** (counts of 0, NULL score) | Inner-join to items and drop them | They are real orders, and a cancellation or conversion rate needs them. Orders are the spine; everything else is `LEFT JOIN`ed in. | 775 orders have no items (603 unavailable, 164 canceled), 768 no review, 1 no payment |
| D22 | **Category name: English, else the Portuguese name, else `unknown`** | Always `unknown` when untranslated; hand-translate the 2 categories | Keeps information that exists. `unknown` is reserved for products with no category at all. | 2 categories (13 products) lack an English name: `portateis_cozinha_e_preparadores_de_alimentos` (10) and `pc_gamer` (3); 610 products have no category |
| D23 | **A seller dimension is included** (`dim_seller`) | Leave sellers out (the brief calls them optional) | The anomaly analysis needs a per-seller late rate. | analytics question 3 |
| D24 | **City and state stay on the address, a deliberate step outside 3NF.** The same goes for the seller. | Split zip into its own table with city and state | A zip prefix does not determine the city or state here, so splitting them off would be a false dependency. | Of 14,994 customer zip prefixes, 39 map to more than one city. Of 2,246 seller prefixes, 34 map to more than one city and 17 to more than one state. |
| D25 | **`dim_date` spans 2016-01-01 to 2018-12-31**, one row per day, with the date itself as the key | Span only the order dates; add a surrogate key | Whole calendar years are tidy and cover the estimated delivery dates, which run past the last purchase. A calendar date is already a stable, unique, readable key. | purchases run 2016-09-04 to 2018-10-17; estimates to 2018-11-12 |
| D26 | **Odd values are kept and documented, not altered.** | Correct or drop them | RAW and staging report what the source said. Judgement belongs in a named model or a documented filter. | 2 payments with 0 installments, 9 payments of 0.00, 4 products of 0 g, 383 items with 0.00 freight |
| D27 | **Geolocation stays out of the model** | Aggregate it to one row per zip prefix | The analysis works at state level, which customers and sellers carry. | carried from the ingest decision |
| D28 | **No SCD2 snapshot** | Snapshot the dimensions | The dataset is a static export, so a history table would show nothing. | |
| D29 | **Four intermediate models:** `int_order_items_rollup`, `int_order_payments`, `int_order_reviews`, `int_customer_orders` | Compute these inside `fct_orders` | Each one rolls a child table up to order grain (the fan-out fix), and `int_customer_orders` ranks each person's orders once, for both `dim_customer` and `fct_orders` to share. | DRY: two marts need the same ranking |
| D30 | **No third-party dbt packages for now.** The composite-key test `unique_combination_of_columns` is a local generic test with the same name and behaviour as the `dbt_utils` one, and the surrogate-key and date-spine helpers for the marts will be local macros too | Install `dbt_utils` | Installing a package downloads and runs someone else's code, which should be confirmed before it happens, and the project needs only three small helpers. Local code is short, readable in the repo and has no supply-chain surface. Swapping in `dbt_utils` later is a small change per use, but the key VALUES would differ (its NULL marker and wording are not the same), so every dimension and fact has to be rebuilt together. | `dbt_project/tests/generic/unique_combination_of_columns.sql`; no `packages.yml` |
| D31 | **Strict casts with an explicit timestamp format:** `cast(...)` and `to_timestamp_ntz(col, 'YYYY-MM-DD HH24:MI:SS')` | `try_cast`, where a bad value silently becomes NULL; letting Snowflake guess the timestamp format | A bad value should stop the build, not vanish: the same rule as `ON_ERROR = ABORT_STATEMENT` in the load. Spelling out the format means a day/month swap cannot pass unnoticed. It is safe today because every column parsed with 0 failures. | `type_and_design_checks.sql` sections 2 to 4 |
| D32 | **The three lineage columns are carried through staging** (`_source_file`, `_source_row`, `_loaded_at`) | Drop them in staging | Any staged row can be traced to its file and record, which is the reason they were captured at load. The marts drop them. | ingest design |
| D33 | **No defensive de-duplication in staging.** Keys are proved by tests that fail loudly. | `qualify row_number() = 1` on every key | No key has a duplicate, so a de-dup would do nothing today. It would also hide a double load, since a forced reload creates duplicates. A failing `unique` test surfaces that, and the tested rebuild path (truncate, reload) removes it. | every key is unique (`relationship_checks.sql` section 1); the key tests pass |
| D34 | **The type rules live in three macros:** `olist_timestamp`, `olist_money`, `olist_integer` | Repeat the cast in every model | One place for the type decisions of D07: change a rule once and every model follows. | used by the 5 models that have timestamps, money or whole numbers |
| D35 | **Tests follow the evidence:** `unique` and `not_null` on every key, `relationships` on every foreign key, `accepted_values` on the three columns with a known small set, `not_null` only where the data has no blanks, and the products-to-category link set to `severity: warn` | `not_null` on every column; failing the build on the 13 untranslated products | A test should catch a real assumption failing. Columns that are legitimately blank get no `not_null` (87,656 review titles are empty). The 13 products are known and handled in the product dimension (D22), so they warn instead of failing, and the warning keeps them visible. | 44 tests: 43 pass, 1 warns with exactly 13 rows, matching the earlier finding |
| D36 | **A singular test compares every staging model's row count with its RAW table** | Rely on the key tests alone | A wrong join or filter could leave the surviving rows unique and still lose rows. Counting catches it. | `tests/staging_row_counts_match_raw.sql` passes for all 8 |
| D37 | **dbt runs from `dbt_project/` with a git-ignored `profiles.yml` built only from environment variables**, and only `build --select` is used | `profiles.yml` in the home folder; `dbt run`; running the whole project | The same settings and key-pair login as the ingest, so there is nothing new to configure and no secret to leak. `build` runs models and tests together, so a model that builds but fails its tests is never treated as done, and a selector stops a typo from running everything. | `profiles.yml.example`; `dbt debug` passed all checks |
| D38 | **Every mart model has an enforced contract**: each column is declared with its type, and every query casts explicitly | Tests only; contracts on the facts only | Snowflake does not enforce types or keys, so the shape of the marts would otherwise be an unwritten promise. With a contract dbt refuses to build a table whose columns or types differ from the declaration, so a change that would break an analyst's query fails the build. It costs one block per model, so it was pulled forward from the optional extras. | all six marts built with `contract: enforced` |
| D39 | **The first order counts every order, whatever its status** | First *revenue* order; first *delivered* order | "First-order experience" is about what a person went through first, and a canceled first order is part of that story. Skipping it would also move the person's cohort and location. The effect is small and visible, and the repeat analysis restricts itself to delivered first orders anyway (D46). | 1,153 of 96,096 people have a canceled or unavailable first order (564 canceled, 589 unavailable); 55 of them ordered again |
| D40 | **`dim_date` is generated inline with Snowflake's `GENERATOR`**, with the row count worked out from the two dates | `dbt_utils.date_spine`; a seed CSV | Nine lines of SQL and no package (D30). Changing a date changes the table and nothing else. | 1,096 rows; no purchase, estimated or delivered date falls outside it |
| D41 | **Foreign keys on the facts are computed from the natural key with the same macro, not looked up by joining the dimension** | Join each dimension to fetch its surrogate key | A join can drop or repeat fact rows; computing the same function on the same natural key cannot. The relationships tests prove every key still lands on a dimension row. The cost is that a fact and its dimension must keep using the same macro. | relationships tests pass for `customer_sk`, `product_sk`, `seller_sk` and the dates |
| D42 | **The surrogate-key macro is `md5` of the values cast to text, a NULL written as a fixed marker, joined with a delimiter** | `dbt_utils` (D30); a sequence or `row_number` | A sequence gives different keys after each rebuild; this gives the same ones. The NULL marker stops NULL and an empty string colliding, and the delimiter stops `('ab','c')` matching `('a','bc')`. Hashing a value that is already a 32-character hash adds nothing but uniformity (D10). | `unique` and `not_null` pass on all four keys |
| D43 | **`primary_payment_type` is the type of the largest payment, a tie going to the earlier `payment_sequential`** | The most frequent type; the first payment | The largest payment is how the customer mainly paid. Without a tie-break the answer for tied orders would depend on row order. | 188 orders tie on their top payment value; 2,246 orders mix payment types; unit test |
| D44 | **Day counts use `DATEDIFF(day, ...)` on dates**, never elapsed hours divided by 24 | Hours / 24 | Matches D18: the estimate is a date, and customers think in calendar days. A delivery at 15:30 on the estimated day is 0 days late. | unit test; delivery days run 0 to 210, median 10 |
| D45 | **Mart checks come in layers:** key and relationship tests, row-count and sum reconciliation against staging, exactly one first order per person, calendar coverage of every date column, unit tests on the rules, and golden numbers | Key tests alone | Each layer catches what the one above cannot: a fan-out leaves every key unique, and a reversed tie-break leaves every total intact. Golden numbers were worked out from RAW before the marts existed, so they are an independent check, and a changed definition should be a deliberate re-pin, which is why they stay a hard failure. | Mutation test: a careless join to the payments table made the unique key (2,961 duplicates), the row-count test (1), the sum reconciliation (5 of 7 measures) and the golden numbers (6 of 9) fail; restored and rebuilt. 6 unit tests pass |
| D46 | **"Came back" has two meanings, kept apart.** `has_multiple_orders` is a plain count of orders. `repeat_after_first_delivery` is true when a later non-canceled order was placed on or after the day the first order was delivered, and NULL when the first order was never delivered. The repeat analysis uses the second one, on delivered first orders only. | One flag for any second order (the first version, `is_repeat_customer`) | A second order cannot be a reaction to a delivery that had not happened. The plain count mixes real returns with baskets split over one session, orders placed before the first arrived and canceled follow-ups, and so overstates the repeat rate by about 1.6 times. Cohorts also differ in follow-up time, so comparisons must hold the window constant. | Of 2,997 people with more than one order: 276 tie on the first timestamp, 897 ordered the same day, 1,070 ordered again before the first delivery and 120 never received it. 1,813 of 93,248 people with a delivered first order returned (1.94%) against 3.12% for the plain count. On-time first delivery 1.99%, late 1.26% (plain count: 3.13% and 2.54%). By delivery quarter the rate falls from 3.5% (early 2017) to 0.46% (mid 2018) |
| D47 | **`revenue` columns hold the answer already filtered:** `revenue` on both facts is the price where the order counts as revenue and 0 elsewhere. Average order value divides by revenue orders that have at least one item. | Only an `is_revenue_order` flag that every query must remember to apply | A bare `SUM(price)` gives 13.59M instead of 13.49M, 0.72% too high, and is an easy mistake under time pressure. 8 revenue-status orders have no items, so they are left out of the average. | revenue 13,494,400.74 from both facts; 98,207 revenue orders of which 98,199 have items |
| D48 | **Order-level measures are copied onto the item fact** (`is_revenue_order`, `is_late`), read from `fct_orders`, and a seller's late rate counts distinct orders | Join the two facts in every query; count units | One definition each. The flag repeats on every unit of an order, so counting units weights multi-item orders, and a multi-seller order counts once for each of its sellers. Money columns of `fct_orders` must not be summed after joining the facts. | by order 6.77% (6,534 of 96,470), by unit 6.59% (7,264 of 110,189); 1,278 orders have more than one seller |
| D49 | **`installments_max` is surfaced in `fct_orders` and `used_voucher` is removed** | Keep a column nothing reads | A column no model uses is something to defend for no reason. The instalment count is a plausible payment-behaviour measure for the campaign question; a voucher is a payment type already visible in `primary_payment_type`. `review_id` and `review_answer_timestamp` stay in the intermediate view to show which review was chosen (D14). | no remaining reference to `used_voucher` |
| D50 | **An independent review of Phase 5 changed D10, D30 and D46 to D49, and left four things alone.** Adopted: the repeat definition, the revenue and late-rate traps, the dead column, three extra tests, six unit tests and the documentation fixes. Not adopted: richer `dim_customer` columns (lifetime revenue, RFM), holiday flags on `dim_date`, and dbt exposures. Not changed: surrogate keys stay (D10), the golden test stays a hard failure (D45), and the date-grain "late" stays (D18, with the timestamp figure documented). | Build every suggestion; ignore the review | Each extra column is another line to defend in a live session, and none answers one of the five questions. The findings were checked against the data before anything changed, and two corrected figures (the repeat rate and the stale wording of D10) would otherwise have reached the memo and the live session. | repeat definition measured in D46; 0 stale references remain |
| D51 | **Q2 covers 2017-01 to 2018-08.** The other months are left out and listed by a second query, so the trimming is visible. | All months; dropping only the first and last | Outside that window the data is a thin sample: 2016 has 329 orders and none at all in November, and September and October 2018 have 16 and 4 against more than 6,000 in a normal 2018 month. A month-on-month change there would be a data gap, not a trend. Explicit dates are easy to defend and to change. | 20 months kept, 5 dropped (Q2b) |
| D52 | **Seller anomalies score only sellers with at least 30 measurable orders, count distinct orders, and show two z-scores.** The flag is the brief's measure (z across sellers above 2); the second (against the platform's 6.77%, scaled by the seller's own volume) is a check. | Score every seller; use only the volume-scaled z; count units | With few orders a single late order moves a rate by 3 points or more, so tiny sellers would top any ranking. A z across sellers ignores volume, so a second opinion that respects it is shown. Distinct orders keep a multi-item order from counting several times (D48). | 627 of 3,095 sellers scored; 24 flagged, all of them also above 2 on the second measure; mean seller late rate 6.52%, standard deviation 4.89 points |
| D53 | **Q5 cohort: people whose first order was delivered, with 180 full days of follow-up. "Returned" = a later non-canceled order placed on or after the delivery day and within 180 days.** | No window; 90 or 365 days | Without a window the rate falls with cohort age purely because later cohorts had less time (3.5% for early 2017 deliveries, 0.46% for mid 2018). Among people who came back the median wait was 79 days and 28.7%, 53.3%, 75.6% and 95.9% had returned within 30, 90, 180 and 365 days. A 365-day window would drop about three quarters of the first deliveries, which came after October 2017; 90 days would miss almost half of the returns; 180 balances the two. | cohort 63,874 (first deliveries up to 2018-04-20), 1,129 returners (1.77%). Counting only orders strictly after the delivery day would give 1,102, so the day rule matters |
| D54 | **Q4 gives each measure its own base and flags thin states.** Delivery days and late % use delivered orders, the review average uses reviewed orders, the freight ratio uses revenue orders, and `enough_data` marks states with at least 100 delivered orders. | One base (all orders) for every measure; dropping small states | Each measure is only defined on some orders (D14, D16, D19), so one base would dilute the late rate with orders that never arrived. Thin states stay, flagged, because dropping them would change the totals. | 27 states; RR (41 delivered), AP (67) and AC (80) are flagged |
| D55 | **Every analytics figure is recomputed from staging by a different route** (`sql/analytics_checks.sql`), and Q1's share uses all revenue as its denominator. | Trust the marts because their own tests pass | The dbt tests show the marts match staging in total. These show the specific numbers the memo will quote, using staging timestamps and natural keys so a mistake in a mart cannot repeat in the check. The share is of the whole business, not of the top 10. | 14 check rows all pass. | D56 | **Insight 1 is checked inside each state, and with the state mix held fixed, before it is claimed.** States with at least 100 late reviewed orders are used (14 of them). | Report the overall late against on-time gap only | Late rates are highest in far-away states, so the gap could be a geography effect. | D57 | **The campaign segment is people whose first order was delivered late OR was reviewed 1 or 2 stars.** Their repeat rate is compared with everyone else's. | Late only; low review only; every first-time buyer | Both are signs of a broken promise, and each shows a lower repeat rate on its own (late 1.21%, 1-2 stars 1.51%, against 1.84% within 180 days). Together they make a segment large enough to test (about 11,900 a year, 16.4% of first-time buyers) without being so broad that it loses its reason. | segment 10,165 people in the 180-day cohort: 0.65% / 0.89% / 1.38% at 56 / 90 / 180 days against 0.91% / 1.20% / 1.84% |
| D58 | **The offer is an apology and free shipping capped at R$15, valid 60 days. The impact table takes its inputs from the data and its uplifts from stated assumptions.** Low is 0.25 points (an apology that only closes the gap to everyone else), base 0.5, high 1.0, in the 8-week repeat rate. | Uncapped free shipping; a percentage discount; uplifts quoted as estimates | Uncapped freight averages R$23.03, so at the base case a voucher needs a margin of about 43% to pay for itself; capping at R$15 (below the R$17.10 median) brings the average cost to R$13.78 and the break-even margin to 18% to 40%.
